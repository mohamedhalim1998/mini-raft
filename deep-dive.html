Architecture

A Raft cluster is a set of servers (typically 3 or 5) that cooperate to maintain a single replicated log. One server is the leader; the rest are followers. Clients send commands to the leader, which appends them to its log, replicates them to followers, and — once a majority has stored an entry — commits it and applies it to the local state machine. Every server contains the same components: a consensus module that runs the Raft protocol, a log, and a state machine that consumes committed entries.

Key Internals

Server States & Terms

Each Raft server is always in one of three states:

  • Follower: Purely passive. It only responds to RequestVote and AppendEntries RPCs. If it receives no communication over an election timeout, it converts to a candidate.
  • Candidate: Used to elect a new leader. It votes for itself and solicits votes from peers.
  • Leader: Handles all client requests and drives log replication. There is at most one leader per term.

Terms are the algorithm's logical clock — monotonically increasing integers, each beginning with an election. Every RPC carries the sender's term. The universal rule: if a server sees a term greater than its own, it updates currentTerm and reverts to follower; if it sees a smaller term, it rejects the request. This single rule neutralizes stale leaders and out-of-date candidates automatically.

Leader Election

Followers expect periodic heartbeats (empty AppendEntries) from the leader. Each runs an election timeout chosen randomly from a range (e.g., 150–300 ms). When it fires without a heartbeat:

  1. The server increments currentTerm and becomes a candidate.
  2. It votes for itself and records votedFor.
  3. It resets its timer and sends RequestVote RPCs to all peers in parallel.

Three outcomes are possible: it wins (majority of votes, becomes leader), it loses (receives AppendEntries from a valid leader, steps down), or a split vote occurs (nobody wins, a new randomized-timeout election follows). Randomized timeouts make split votes rare and self-correcting.

A server grants its vote only if (a) it has not already voted this term, and (b) the candidate's log is at least as up-to-date as its own.

Log Structure & Log Replication

The log is an array of entries, each holding a state-machine command and the term in which the leader created it. Entries are identified by their index. Once elected, the leader:

  1. Appends a client command to its own log.
  2. Sends AppendEntries RPCs to all followers in parallel.
  3. Each RPC includes prevLogIndex and prevLogTerm — the entry immediately preceding the new ones.
  4. A follower accepts only if its log matches at prevLogIndex/prevLogTerm. Otherwise the leader decrements nextIndex and retries, walking back until logs agree, overwriting any conflicting suffix.

This produces the Log Matching Property: if two entries in different logs share an index and term, they store the same command and all preceding entries are identical. The leader tracks nextIndex[] (next entry to send) and matchIndex[] (highest replicated) per follower.

Commitment & Applying Entries

An entry is committed when the leader that created it has replicated it on a majority of servers. The leader finds the highest index N such that matchIndex >= N on a majority and log[N].term == currentTerm, sets commitIndex = N, applies through it, and returns results to clients. It piggybacks commitIndex on subsequent AppendEntries so followers apply the same entries in the same order.

Critical subtlety: a leader may only directly commit entries from its own term. It must never conclude an entry from a previous term is committed just because it sits on a majority (Figure 8 in the paper). Older entries become committed indirectly, once a current-term entry commits on top of them.

Safety Guarantees

Raft guarantees five properties that together ensure state machines never diverge:

PropertyGuarantee
Election SafetyAt most one leader can be elected in a given term.
Leader Append-OnlyA leader never overwrites or deletes entries in its own log; it only appends.
Log MatchingIf two logs share an entry with the same index and term, they are identical up to that index.
Leader CompletenessIf an entry is committed in a term, it is present in the logs of all leaders of higher terms.
State Machine SafetyIf a server applied an entry at an index, no other server applies a different entry for that index.

The keystone is the Election Restriction: a candidate cannot win unless its log is at least as up-to-date as a majority. "Up-to-date" compares last entries' terms; higher term wins, and on a tie the longer log wins. This ensures the winning leader already holds all committed entries.

Persistence & Recovery

Before responding to any RPC, a server must persist three pieces of state to stable storage:

  • currentTerm — the latest term seen.
  • votedFor — the candidate voted for this term (or null).
  • log[] — the log entries.

commitIndex and lastApplied are volatile and safely rebuilt after restart. Persisting term/vote prevents double-voting in a term; persisting the log prevents loss of committed data. On restart a server comes up as follower, loads persisted state, and the leader's consistency check reconciles any lagging log.

Log Compaction & Snapshots

A log that grows forever wastes space and slows restarts. Snapshotting is Raft's compaction mechanism: each server independently writes a snapshot of its state machine up to some index, recording lastIncludedIndex and lastIncludedTerm, then discards entries through that index.

When a follower lags so far that the leader has already discarded the entries it needs, the leader sends an InstallSnapshot RPC transferring the snapshot directly. The follower installs it, discards any conflicting prefix, and resumes normal replication.

Cluster Membership Changes

Changing the server set is dangerous: you cannot switch every server atomically, so two disjoint majorities could elect two leaders. Raft solves this with joint consensus, a two-phase approach:

  1. The leader appends a joint configuration entry (C-old,new). While active, agreement requires separate majorities from both the old and new configurations, making two independent leaders impossible.
  2. Once C-old,new commits, the leader appends the new configuration (C-new). Once C-new commits, the transition is complete.

Configuration changes take effect the moment an entry is appended (not committed), and a server always uses the latest configuration in its log. Many production systems (etcd, HashiCorp Raft) instead use the simpler single-server change — adding/removing one server at a time — preserving majority overlap without joint consensus. Learner/non-voting members are often added first so a new server can catch up before counting toward quorum.
